# E12 Installer für alle Systeme und Release-Bau

Status: gilt. Die Regeln dazu stehen im Index der [CLAUDE.md](../../CLAUDE.md). Ergänzt [E4](0004-schluesselbund-und-verbindung.md), [E8](0008-einstellungsfenster.md) und [E11](0011-einstellungsfenster-auf-dem-mac.md) um Windows und Linux; keine Ausnahme zu A1 bis A7. Was moocp von einem Installer erwartet und wie es Updates sucht, steht in dessen README (Teil 4, „Plugins“).

## Entscheidung

**Ein Release, drei Installer.** Ein veröffentlichtes Release baut die getaggte Revision auf Linux x64, Windows x64 und macOS arm64, jeweils auf einem Runner dieses Systems (kein Cross-Build, keine Abhängigkeit von einem Arbeitsrechner), und hängt `<kurzname>_linux_x64_<Version>.tar.gz`, `<kurzname>_setup_<Version>.exe` und `<kurzname>_setup_<Version>.pkg` samt `.sha256` an dasselbe Release. Die Namen `.exe` und Version folgen der Update-Prüfung von moocp, die den Installer im Release anhand von Tag und GitHub-Prüfsumme findet und prüft. Andere Prozessoren sind nicht vorgesehen: `dart compile exe` übersetzt nur für den eigenen.

**Eine Revision, kein Mischen.** Ein Job legt eine SHA fest, jeder Bau checkt genau diese aus, und der Artefaktname trägt sie. Beim Release müssen Tag, `version` in `plugin.json` und die Versionen beider `pubspec.yaml` übereinstimmen, und der Tag muss auf die gebaute Revision zeigen; vor dem Hochladen wird das noch einmal gegen den Tag geprüft. Hochgeladen wird nur, wenn alle drei Systeme bestanden haben; fehlt eines, scheitert der Lauf sichtbar und das Release bleibt ohne Installer. Nach dem Hochladen wird die Prüfsumme jeder Datei im Release gegen die gebaute verglichen. Ein manueller Lauf (`workflow_dispatch`, wählbare Revision) und eine Pull Request bauen und prüfen dasselbe, veröffentlichen aber nie.

**Schreibrecht nur zum Veröffentlichen.** `contents: write` hat allein der Veröffentlichungsjob, und der läuft nur bei einem Release im eigenen Repository. Pull Requests von Forks laufen mit lesendem Token. Die Aktionen sind auf Commits festgelegt, Flutter ist auf 3.50.0 (Dart 3.14) festgelegt, das beide Pakete erfüllen; Abhängigkeiten werden mit `--enforce-lockfile` aufgelöst. Es braucht keine Signatur; macOS und Windows warnen bei ungesignierten Installern, die README sagt, wie man sie öffnet.

**Prüfung auf jedem System.** Analyse, Tests, Bau und Installer laufen auf dem System des Installers. Unter Windows laufen die Tests, die das System selbst ansprechen; das Testgerüst benutzt sh-Skripte und bleibt Linux und macOS. Danach wird der Installer so benutzt, wie die Lehrkraft ihn benutzt (`tool/smoke.sh`: still installieren, Update, laufendes Plugin, Deinstallation) und der installierte Ordner geprüft (`tool/smoke.dart`: Inhalt, Skill-Erkennung, Start wie durch moocp, Lesen im lokalen Kontextbereich, Einstellungsfenster öffnet und bleibt offen). Unter Linux läuft das Archiv zusätzlich auf einem sauberen Debian 13 mit nur den Laufzeitpaketen, ohne Dart und Flutter.

**Windows.** Das Fenster ist ein Flutter-Windows-Bau (`fenster/windows/`), `bauen.ps1` legt es als `einstellungsfenster\kontext_einstellungen.exe` in den Plugin-Ordner. Die Einstellungen liegen in `%APPDATA%\moocp-contextmanager`. Das Passwort liegt in der Anmeldeinformationsverwaltung (`CredReadW`/`CredWriteW` über `dart:ffi`, als allgemeiner Eintrag `moocp-contextmanager:<Konto>`, UTF-16, lokal je Rechner): Es geht nur im Speicher an das System, nie über Kommandozeile, Datei oder Protokoll, und es gibt keinen Ersatz über eine Datei (ergänzt E4). Ein Rest des Fensters aus einem früheren Lauf wird über PowerShell (`Win32_Process`) als unser Fenster erkannt. SIGTERM gibt es unter Windows nicht; dort endet das Plugin mit der Standardeingabe wie von moocp gestartet. Der Installer ist ein NSIS-Skript nach dem Muster des Beispiel-Plugins von moocp (`installer/windows/plugin.nsi`, gebaut von `create_installer.bat`): nur für den Benutzer, nach `%APPDATA%\moocp\plugins\<kurzname>`, Abbruch ohne moocp, Abbruch bei laufendem Plugin ohne einen Prozess zu beenden, Plugin-Ordner ganz ersetzt, Uninstaller im Plugin-Ordner.

**Linux.** Das Archiv enthält den Plugin-Ordner (`plugin/`) und `installieren.sh`. Das Skript installiert nach `$XDG_CONFIG_HOME/moocp/plugins/<kurzname>` (nur ein absoluter Wert gilt, sonst `~/.config`), lehnt root ab, bricht ohne moocp ab, bricht bei einem laufenden Programm aus dem Plugin-Ordner (Plugin oder Fenster, an `/proc/<pid>/exe` erkannt) mit der Bitte ab, moocp zu schließen, beendet nie einen Prozess, ersetzt nur den Plugin-Ordner (erst vollständig daneben ablegen, dann tauschen) und fasst Einstellungen, Ausstand und Schlüsselbund nie an; `--entfernen` löscht den Plugin-Ordner. Das Plugin-Archiv ist ein Ordner, kein Paket des Systems: Es braucht weder Administratorrechte noch eine Paketverwaltung. Laufzeitabhängigkeiten stehen in der README (`libsecret-tools` für WebDAV-Passwörter, GTK 3 und `libsecret` für das Fenster).

## Verworfen

Mit Docker oder QEMU für andere Systeme bauen: Es beweist nichts über das echte System. Signieren und notarisieren: Es braucht Entwicklerkonten, die das Projekt nicht hat. `.deb`, AppImage oder `.run` für Linux: Das ersetzt den Plugin-Ordner nicht nach den Regeln von moocp, und ein Paket des Systems braucht Administratorrechte. Passwort über `cmdkey` oder PowerShell speichern: Das Passwort stünde in einer Kommandozeile oder einer Skriptdatei. Das Release als Entwurf vorbereiten und die Installer von Hand anhängen: Dafür gäbe es keine Zusicherung, dass alle drei aus derselben Revision stammen.
